    5. La vista y su modelo

    5.1. Introducción

    Volvamos a la arquitectura de una aplicación ASP.NET MVC:

    En el capítulo anterior, examinamos cómo ASP.NET MVC presenta información de solicitud [1] a una acción [2a] en forma de un modelo que puede contener restricciones de validación. Este modelo se pasa como entrada a la acción, y nos referimos a él como el modelo de acción. En se centrará ahora en el resultado más común de una acción, el tipo [ViewResult], que corresponde a una vista V [3] acompañado de su modelo M [2c]. Este modelo se denominará el modelo de vista V, no confundir con el modelo de acción que acabamos de estudiar. Uno es la entrada a la acción, el otro es la salida.

    Empecemos creando un nuevo proyecto [Ejemplo-03] [1] dentro de la misma solución, del tipo básico ASP.NET MVC:

    Vamos a crear un controlador llamado [Primero] [2]. El código generado para este controlador es el siguiente:

    
using System.Web.Mvc;
 
namespace Example_03.Controllers
{
  public class FirstController : Controller
  {
    public ActionResult Index()
    {
      return View();
    }
 
  }
}

    • el primer parámetro es el nombre de la vista. Si se omite, la vista utilizada será la que tenga el mismo nombre que la acción que produce el [ViewResult], y se buscará en la carpeta [/Views/{controller}], donde {controller} es el nombre del controlador;
    • la segunda es la plantilla de la vista. Si se omite, la vista no tiene plantilla.

    5.3. Utilizar un modelo fuertemente tipado para pasar información a la vista

    El método anterior tiene el inconveniente de no permitir la detección de errores antes de la ejecución. Así, si la vista [Action01.cshtml] utiliza el código

    
<h4>@ViewBag.Info</h4>

    Se producirá un error porque la propiedad [Info] no existe. La creada por la acción [Action01] se llama [info]. Por lo tanto, podemos utilizar un modelo fuertemente tipado para evitar este problema.

    En uno de los ejemplos comentados anteriormente, la acción era la siguiente:

    
    // Action10
    public ContentResult Action10(ActionModel03 model)
    {
      string errors = getErrorMessagesFor(ModelState);
      string text = string.Format("email={0}, day={1}, info1={2}, info2={3}, info3={4}, errors={5}",
        model.Email, model.Day, model.Info1, model.Info2, model.Info3, errors);
      return Content(text, "text/plain", Encoding.UTF8);
}

    La acción [Action10] estaba pasando seis piezas de información (Email, Día, Info1, Info2, Info3, errores) a su cliente como una cadena. Pasaremos esta información a un modelo de vista [ViewModel01]. Como este modelo utiliza información de [ActionModel03], lo derivaremos de esa clase.

    Empezaremos copiando [ActionModel03] del proyecto [Example-02] en el proyecto actual [Example-03]:

    y cambiamos su espacio de nombres para que coincida con el del proyecto [Example-03]:

    
using System.ComponentModel.DataAnnotations;
namespace Example_03.Models
{
  public class ActionModel03
  {
    [Required(ErrorMessage = "The email parameter is required")]
    [EmailAddress(ErrorMessage = "The email parameter is not in a valid format")]
    public string Email { get; set; }
 
    [Required(ErrorMessage = "The day parameter is required")]
    [RegularExpression(@"^\d{1,2}$", ErrorMessage = "The day parameter must be 1 or 2 digits")]
    public string Day { get; set; }
 
    [Required(ErrorMessage = "The info1 parameter is required")]
    [MaxLength(4, ErrorMessage = "The info1 parameter cannot be longer than 4 characters")]
    public string Info1 { get; set; }
 
    [Required(ErrorMessage = "The info2 parameter is required")]
    [MinLength(2, ErrorMessage = "The info2 parameter must be at least 2 characters long")]
    public string Info2 { get; set; }
 
    [Required(ErrorMessage = "The info3 parameter is required")]
    [MinLength(4, ErrorMessage = "The info3 parameter must be exactly 4 characters long")]
    [MaxLength(4, ErrorMessage = "The info3 parameter must be exactly 4 characters long")]
    public string Info3 { get; set; }
  }
}

    Hemos mencionado que si no se marcaba o seleccionaba ningún valor para los campos [CheckBoxesField, SimpleChoiceListField, MultipleChoiceListField], los parámetros correspondientes no formaban parte de la cadena publicada y, por tanto, las propiedades del modelo con los mismos nombres no se inicializaban.

    • en [2], el [POST] devuelve una casilla de verificación marcada.

    La explicación es la siguiente:

    • debido a que no hay casillas de verificación seleccionadas, el parámetro [CheckBoxesField] no se incluye en los valores contabilizados;
    • la acción [Action08Post] procede como sigue: 
    
    [HttpPost]
    public ViewResult Action08Post(ApplicationModel application, FormCollection posted)
    {
      ViewBag.info = ...
      ViewModel08 model = new ViewModel08(application);
      TryUpdateModel(model, posted);
      return View("Form", model);
}
    • Línea 5: El modelo de formulario es instanciado. Sin embargo, el constructor utilizado asigna el array ["2"] a la propiedad [CheckBoxesField];
    • Línea 6: Los valores contabilizados se guardan en el modelo. Como el parámetro [CheckBoxesField] no forma parte de los valores publicados, no se asigna un valor a la propiedad del mismo nombre.     [HttpPost]
    public ViewResult Action08Post(ApplicationModel application, FormCollection posted)
    {
      ViewBag.info = string.Format("Controller={0}, Action={1}", RouteData.Values["controller"], RouteData.Values["action"]);

      TryUpdateModel(model, posted);
      // processing of non-posted values
      if (posted["CheckBoxesField"] == null)
      {
        model.CheckBoxesField = new string[] { };
      }
      if (posted["SimpleChoiceListField"] == null)
      {
        model.SimpleChoiceListField = "";
      }
      if (posted["MultipleChoiceListField"] == null)
      {
        model.MultipleChoiceListField = new string[] { };
      }
      // display form
      return View("Form", model);
    }

    Los atributos [data-x] de las etiquetas generadas son utilizados por el JavaScript que hemos incrustado en la vista. Si falta este JavaScript, estos atributos simplemente se ignoran, y no hay validación del lado del cliente. Funciona igual que en el ejemplo anterior. De ahí el término [discreto] para esta técnica.
